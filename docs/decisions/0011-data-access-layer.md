# 0011. Data access layer (ORM, driver, and session conventions)

- **Status:** **Accepted** — approved by the project owner on 2026-10-13
- **Date:** 2026-10-13
- **Deciders:** project owner
- **Related requirements:** PR-001, PR-002, PR-003, PR-011
- **Related documents:** [`0008`](0008-database-identity-and-migrations.md), `docs/DATABASE.md` §5/§7/§8, `docs/AGENT_RUNTIME.md`, `ARCHITECTURE.md`, `docs/PERFORMANCE.md`

> **Owner decision (2026-10-13):** Approve the SQLAlchemy asynchronous data-access layer, with **explicit transaction boundaries**, **session-per-request/service conventions**, **no lazy loading in async contexts**, and **no database connection held during model or tool calls**.

## Context

`docs/DATABASE.md` §12 and [`0008`](0008-database-identity-and-migrations.md) both recorded the ORM/driver choice as unresolved, and 0008 explicitly noted that "both decisions belong in `docs/decisions/` as ADRs once made". No record owned it, so there was no path to acceptance and an implementer would have had to invent the data-access layer — how sessions are created and closed, where transactions begin and end, how reads are expressed, and how the async model is respected.

This choice has consequences independent of the schema itself (0008): it fixes the async session lifecycle, how connection pooling is configured, how transaction boundaries are expressed in code, how much of Alembic's autogeneration can be trusted, and how easy it is to accidentally hold a connection across a slow model or tool call — which `ARCHITECTURE.md` and `docs/DATABASE.md` §7 both forbid.

## Decision

**SQLAlchemy 2.x, asynchronous, with `asyncpg` as the driver.**

1. **Async engine and sessions.** One async engine per process, created at startup, disposed at shutdown. `asyncpg` driver via the `postgresql+asyncpg://` DSN.
2. **Session-per-request / session-per-service-unit.** The API creates one session per request, scoped to the request lifecycle through a FastAPI dependency, and closes it on exit. The worker creates one session per job-claim or per step, not one per process. Sessions are never module-level globals and never shared across concurrent tasks — a single `AsyncSession` is not safe for concurrent use.
3. **Explicit transaction boundaries.** Transactions are opened and committed **explicitly** at the service layer, matching the transaction list in `docs/DATABASE.md` §5. No implicit commit-on-exit, and no "auto-commit" mode. A state change and its `task_transitions` / `task_events` / `audit_events` rows commit **together or not at all** — this is the invariant the schema depends on.
4. **No lazy loading in async contexts.** Async lazy loading raises or silently performs I/O at an unpredictable time. Use explicit eager loading (`selectinload` / `joinedload`) or explicit second queries. Relationship defaults must not be relied upon to fetch data implicitly.
5. **No database connection held across a model or tool call.** This is the single most important operational rule here. Read what is needed, close or release the transaction, perform the model/tool call, then open a new short transaction to persist the result. Holding a pooled connection for the duration of an LLM call exhausts the pool under trivial concurrency and is explicitly forbidden by `ARCHITECTURE.md` §8 and `docs/DATABASE.md` §7.
6. **Models are the schema's source for Alembic, but autogenerated diffs are always reviewed.** Autogeneration is a convenience, not an authority; every revision is read before it is applied.
7. **Pooling and timeouts** follow `docs/DATABASE.md` §7, with separate pools and least-privilege roles for the API and the worker.
8. **Query discipline.** No N+1 access from the API; list views must not load large payloads; bounded statement and lock timeouts; indexes justified by measured query patterns rather than speculation.

## Alternatives considered

- **Raw `asyncpg` with hand-written SQL.** Genuinely viable: maximum control, minimal abstraction, no ORM impedance, and the fastest path for hand-tuned queries. Rejected for the MVP because it forfeits typed models, requires hand-maintaining row mapping, and weakens the coupling to Alembic's autogeneration — all of which cost more than the abstraction does at MVP scale. **Reasonable to revisit for specific hot paths** if measurement shows ORM overhead matters; a single decision per query, not a rewrite.
- **SQLModel.** Attractive because it unifies Pydantic schemas and ORM models, reducing duplication. Rejected: it constrains the Pydantic layer to the ORM's model shape, which conflicts with keeping API contracts independent of persistence — and `docs/API_CONTRACTS.md` §8.4 already treats the contract as external and generated. The coupling is a liability for a project that intends to version its contract separately.
- **A lightweight query builder (for example Piccolo, or SQLAlchemy Core without ORM).** Reduces magic while keeping typed queries. Rejected as a middle path that gives up the ORM's migration integration without the full control of raw SQL.
- **Synchronous SQLAlchemy with a thread pool.** Rejected outright: it reintroduces blocking behavior that the async FastAPI handlers and the worker must not have, and it makes the "never block the event loop" rule unenforceable.
- **A second, non-SQLAlchemy access path for the worker.** Rejected: two access layers mean two transaction conventions and two sets of bugs. One layer, one set of rules.

## Consequences

**Positive.** Typed models with a single source of truth for the schema; Alembic integration that 0008 depends on; explicit transaction boundaries that make the schema's atomicity invariants expressible and testable; pooled connections configured in one place.

**Negative / accepted costs.** An ORM abstraction sits between the code and the SQL, which can obscure query cost — mitigated by requiring `EXPLAIN` on hot paths and by the "no connection across a model call" rule. Lazy-loading traps are real in async code and must be actively avoided. Autogenerated migrations can be wrong and must always be reviewed. ORM overhead is measurable and may need targeted raw-SQL exceptions later.

**Risks to manage.** The most likely operational failure is a session or transaction left open across a slow external call; that must be caught by a test or a metric, not by review alone. The second most likely is an accidental concurrent use of one `AsyncSession`, which produces confusing errors.

## Verification

- **Unit:** a service function that performs a model call does not hold an open transaction across it (assert observable via pool metrics or an instrumented session).
- **Integration:** a state change without its accompanying `task_transitions` / `task_events` rows is impossible — the transaction rolls back together.
- **Load:** pool saturation remains bounded under concurrent requests that each perform a slow simulated model call. Connection checkout wait is measured and reported per `docs/PERFORMANCE.md`.
- **Integration:** an async read path that would require lazy loading fails loudly rather than performing hidden I/O.
- **Review:** every Alembic revision was read before being applied; no revision edited after being applied to a shared environment.

## Remaining items

These do not block implementation but must be settled during Milestone 1–2:

- **Pool sizing and timeout values.** Proposed: API pool 5–10 connections, worker pool 2–4, statement timeout 5 s, lock timeout 2 s, connection checkout timeout 5 s. To be validated against measured load before production.
- **Whether any hot-path query is exempted to raw SQL**, and on what measured evidence. Default answer: no exemptions until measurement justifies them.
- **Read-model/materialized-view strategy** if list views become expensive. Deferred until measured; `docs/DATABASE.md` §11 already anticipates it.
