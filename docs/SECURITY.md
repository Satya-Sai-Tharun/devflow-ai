# Security Baseline

**Status:** Minimum intended security requirements. Concrete controls must be verified in implementation and tests.

## 1. Security principles

- Least privilege and deny-by-default tool access.
- Defense in depth; do not rely on model compliance as a security control.
- Explicit authorization and approval for consequential operations.
- Isolation between orchestration, tools, and execution environments.
- Auditable decisions without logging secrets.
- Fail closed when policy, identity, or approval status cannot be established.

## 2. Identity and authorization

- Authenticate users before exposing private tasks or project data.
- Enforce authorization on the server/API boundary, not only in the UI.
- Scope access to projects, tasks, tools, and credentials.
- Re-check authorization when a delayed or resumed workflow executes an action.
- Do not trust client-supplied user IDs, roles, or approval flags without verification.

## 3. Tool and command execution

- Maintain an explicit allowlist of tool names and capabilities.
- Validate tool arguments against schemas and enforce size/time limits.
- Avoid arbitrary shell execution by default.
- Run commands in a constrained, isolated workspace with limited filesystem and network access.
- Restrict working directories and reject path traversal or unexpected paths.
- Apply timeouts, output limits, cancellation, and bounded retries.
- Record tool identity, sanitized arguments, policy outcome, timestamps, and result status.
- Do not treat a tool request generated by a model as authorization.

## 4. Human approval

Require explicit approval for configured high-impact operations, such as destructive filesystem changes, external publication, production changes, deployment, merges, or access to sensitive resources. Define the precise policy before enabling these operations.

Approval records should identify the action and scope, requester, approver, decision, timestamp, and policy context. Reject stale or mismatched approvals. Do not execute if approval is missing, ambiguous, or cannot be verified.

## 5. Prompt injection and untrusted content

Treat repository files, issue descriptions, web pages, retrieved documents, logs, code comments, and model outputs as untrusted. They may contain malicious or conflicting instructions.

- Separate trusted policy/instructions from retrieved context.
- Do not allow retrieved text to modify authorization or tool policy.
- Minimize the amount of context sent to external model providers.
- Validate outputs before using them as tool arguments or executable code.
- Include prompt-injection and tool-abuse scenarios in security tests.

## 6. Secrets and sensitive data

- Never commit credentials, tokens, private keys, or production secrets.
- Use environment variables or an approved secret manager.
- Redact sensitive values from logs, traces, error messages, prompts, and reports.
- Keep permissions and credential lifetime as narrow as practical.
- Rotate and revoke exposed credentials promptly.
- Do not copy user secrets into generated documentation or test fixtures.

## 7. Data protection and persistence

- Define what task, code, and event data is stored and for how long before production use.
- Restrict access to task histories and artifacts.
- Validate inputs and encode outputs appropriately for their destination.
- Avoid storing more personal or sensitive data than necessary.
- Define backup, deletion, retention, and incident-response requirements before production deployment.

## 8. Dependencies and supply chain

- Use trusted package sources and review dependency additions.
- Keep dependency manifests and lockfiles consistent.
- Run available vulnerability and secret scanning in CI when configured.
- Do not disable security checks merely to make builds pass.
- Pin or constrain tool versions using the project's existing conventions.

## 9. Audit and incident handling

Record security-relevant events, including denied tool calls, approval decisions, permission changes, execution failures, and suspicious inputs. Logs should support investigation without exposing secrets.

When a potential incident is found: stop the risky action, preserve relevant sanitized evidence, notify the project owner, and follow the project's incident process. Do not attempt destructive cleanup or credential changes without appropriate authorization.

## 10. Required security tests

At minimum, test:
- Unauthorized users cannot access another user's/project's task data.
- Unknown or disallowed tools are rejected.
- Invalid and oversized tool arguments are rejected.
- Gated actions do not execute without valid approval.
- Expired or mismatched approvals are rejected.
- Path traversal and out-of-workspace access are blocked.
- Secrets are not emitted in logs or final reports.
- Retrieved prompt-injection content cannot override trusted policy.
- Timeouts and policy-service failures do not become success.

## 11. Release gate

Do not describe the system as production-secure based on this document alone. Security claims require implementation evidence, test results, and review of the actual deployment configuration.
